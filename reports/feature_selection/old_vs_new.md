# Feature selection: the published 22 against the set this project now declares

**Card #25 · PRD S7, R4.** `REPORT.md` §3.2 lists 22 features. They were chosen by
`Boruta_FeatEng.py`, fitted once over all 896 training rows, and the cross-validated scores in
the same report were then computed over those same rows — leak **L6**, the PRD's second named
leak. Card #24 ported that selector honestly: the three stages it really has, reading
CleanLab-screened rows, run inside the five outer folds of card #88's group-aware protocol. This
is what changed.

Regenerate this document — it is generated, not written:

```bash
python -m hydms.surrogate.select --emit-comparison
```

The tables it reads are published beside it. They came from a five-fold run at the configured
Boruta budget on **2026-09-05**, about fifty minutes of fitting, and from the single-pass runs
described under *Which comparison each column is*. **The first result stands:** this document is
not re-run until there is a better reason than disliking it.

## Which comparison each column is

Four things are being compared and only two of them are results. Saying which is which is the
point of this section: the published 22 and the new 14 were **not** produced under the same
protocol, the same rows, or the same candidate pool, and a table that puts them side by side
without saying so invites exactly the reading it should prevent.

**1. `selection-per-fold.csv` — five outer folds, screened, 21 candidates. The result.** Each
fold selects on its own training rows; the rows it is scored on never reach the selector. This
is the only column that is a claim about hydrogen storage rather than about a fit.

**2. `selection-once.csv` — one screened pass over the whole training split.** `python -m
hydms.surrogate.select --once`. **This is leak L6**, deliberately reproduced: it is the archival
*shape* run with this project's data hygiene, and the command says so in its own output. It is a
column of this comparison, never a result.

**3. `selection-once-all-features.csv` — one screened pass, 700 rows, 22 candidates.** `python
-m hydms.surrogate.select --once --all-features`. The same leaking shape with
`dev_Gordy_electonegativity` put back, which costs 266 of 1,279 curated rows and leaves 700
training rows to select on against 893. It is the closest reproducible thing to the pool the
published 22 came from, and **it does not select the feature that defines that pool**: Boruta
rejects `dev_Gordy_electonegativity` on the 629 screened rows it survives on, having been
offered it. Its 16 are a subset of the 18 the 21-candidate pass selects, which in turn contain
the consensus 14: every reading of this run nests inside the next, so the disagreement between
them is about how far to cut, never about direction.

**4. `REPORT.md` §3.2's 22 — not reproducible.** The pipeline that produced them cannot be run
end to end (`docs/FREEZE.md` §Why), the order they were trained in was never committed, and the
`gordy_en` column CBFV supplied for them is not in the citable 2024 Oliynyk table. The 22 are
therefore quoted here as *published*, never as reproduced.

## Computability: the axis SHAP does not measure

A feature that cannot be computed for a composition does not cost accuracy — it costs **rows**,
and this dataset has 1,279 of them. 7 of the published 22 are charged anything at all:

| feature | rows_blocked | blocking_elements |
| :--- | ---: | :--- |
| dev_Gordy_electonegativity | 266 | Ce, Dy, Er, Eu, Gd, Hf, Ho, Ir, Lu, Nd, Os, Pr, Pt, Re, Sm, Ta, Tb, Th, Tm, U, W |
| avg_polzbl_divi_atom_mass | 1 | Eu |
| dev_atom_mass_mult_therm_cond | 1 | Eu |
| avg_is_alkaline | 1 | Eu |
| dev_bp_divi_atom_mass | 1 | Eu |
| range_first_ion_en_mult_X | 1 | Eu |
| dev_voro_coord_divi_mol_vol | 1 | Eu |

`dev_Gordy_electonegativity` alone costs **266 of 1,279 rows** (20.8%), because the citable 2024
Oliynyk table leaves `gordy_en` blank for 21 of the 55 elements these rows use. Card #24
measured both sides of that trade and settled it — **drop the feature, keep the rows** — and
this run is the other side of it: with the feature back in the pool, selection has 700 training
rows instead of 893. And on those rows Boruta **rejects it** — where card #24's controlled
comparison, fitted on all 700 of them, confirmed it. Same pool, same seed, same budget; the 71
rows screening drops are the only difference, and they reverse the verdict. The trade was
settled on rows rather than on importance, and this is why it had to be.

The remaining 6 are charged **one row each**, all of them the same row: `Eu1Ni5`, whose europium
the JARVIS table does not serve. Dropping any of them would buy nothing.

**What this means for the new set.** The consensus 14 costs the same single row the 21-feature
pool does. The computability gain in this comparison is entirely card #24's Gordy trade; the
consensus cut is free on this axis and is justified on the stability one below.

## The columns were not produced under equal statistical power

| fold | rows_offered | rows_fitted | removed | flagged | held_out | selected |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| outer-0 | 708 | 635 | 73 | 71 | 185 | 20 |
| outer-1 | 716 | 571 | 145 | 144 | 177 | 16 |
| outer-2 | 721 | 704 | 17 | 15 | 172 | 18 |
| outer-3 | 717 | 671 | 46 | 45 | 176 | 18 |
| outer-4 | 710 | 654 | 56 | 54 | 183 | 19 |

Each fold selects 16-20 of 21; the whole training split selects 18 on 864 rows. **Fewer rows
make Boruta less able to reject**, because a weak feature is harder to separate from its shadow
— so a protocol that gives each fit fewer rows is not merely a different answer, it is a *less
selective* one. The new N may not be read beside the old 22 as though the two had been produced
under the same power.

**How far that can be pushed here, honestly: not very.** Three runs of this selector exist over
the same candidates, and they differ in more than one variable each, so the direction can be
stated and the size cannot. The unscreened whole-split probe card #24 ran fits 893 rows and
selects 14; screened, the same pass fits 864 and selects 18; the folds fit 571-704 and select
16-20. Row count and screening move together across all three, and screening is not a neutral
thinning — it removes the rows CleanLab finds least consistent, which is a change in what Boruta
is separating signal from as well as in how much of it there is.

**Within the folds, the row count does not order the answers at all.** `outer-1` fits on 571
rows and selects 16; `outer-2` fits on 704 and selects 18. That is a 133-row spread — CleanLab
removes 17 rows from one fold and 145 from another, of roughly 714 offered — with no monotone
effect on how many features come out. Whatever separates the folds is *which* compositions were
held out, not how many rows survived, and that is the argument for reading the consensus rather
than any single fold.

(Removals exceed CleanLab's flags by the exact-duplicate and malformed-formula findings the same
stage drops, which are properties of the rows rather than of CleanLab.)

## `dev_voro_coord_divi_mol_vol` rests on a placeholder for 18 rows — and stays

Card #18 found that the JARVIS table stores `voro_coord` = 1.0 for `Cs` (0 rows), `Gd` (18
rows), where every other element it serves is between 3 and 12. That is not a coordination
number; it is filler. One consensus feature is built on it, and whether it survives is this
card's call.

**It stays.** It is selected by all five folds, the exposure is 18 of 1,279 curated rows (1.4%),
and removing a feature the selector chose unanimously — by hand, after seeing the result — is
the kind of decision this phase exists to remove, not to relocate. CBFV reads the same column,
so gate AC-2's parity is unaffected either way: this is a limit of the *source table*, not a
disagreement between two implementations of it.

What follows from keeping it is a statement, not a silence: for those 18 rows the feature is
computed from filler rather than from a measurement, and the model card owes that sentence.
`hydms.descriptors.composites.disagreements("jarvis")` lists the related defect — eleven
`*_mult_voro_coord` columns that are 0.0 for the same elements — none of which is in this pool
or could be, since the pool did not widen.

## What was considered and not done

**The union (21).** It is the candidate pool. A "selection" that returns everything it was
offered is not a selection, and publishing it would mean reporting that selection has no effect
while the folds plainly disagree with each other.

**A threshold in between** — 4 of 5, or 3. Every one of them is a cut chosen *after* seeing
which features fell where. This phase exists because decisions were made after seeing the data;
adding one here would move the defect rather than fix it.

**The refit reading — publish the whole-split answer.** There is a real argument for it: in
nested cross-validation the folds estimate the *procedure*, and the deployed model refits the
whole procedure, selection included, on all the training rows. Under that reading the published
set would be the 18 of `selection-once.csv`. It was not taken, for a reason specific to this
thesis: Chapter 3 reports the feature set **as a finding**, and a set produced by a single fit
carries no evidence about its own stability — this run has just shown there is none to assume.
The consensus is the part of that answer the instability finding does not touch, and it is a
subset of the whole-split answer, so choosing it contradicts nothing.

**Re-running until the sets agree.** The card forbids it and it would be 21-way multiple testing
on one dataset.

## What this does not claim

- **Not that the new set is better.** No model has been fitted on either set. Cards #26-#30 do
  that, and #29's bootstrap intervals are what would license a comparison of scores. This
  document compares *selections*, not performance.
- **Not that the published 22 were wrong.** They were chosen by a procedure whose score was
  reported over the rows that chose them. The defect is in the reporting, and it means the 22
  come with no honest evidence either way.
- **Not that 14 is a number about hydrogen storage.** It is the number of features that survived
  a five-fold group-aware cut of an 893-row training split. A different dataset of this size
  would produce a different one, and the stability table above is the honest statement of how
  different.
- **Not that no fold model used the other features.** Each fold selected its own 16-20, which is
  what keeps the score honest. The declared set is what a *shipped* model is fitted on, and #26
  and #29 owe the sentence that says which of the two any published number belongs to.
