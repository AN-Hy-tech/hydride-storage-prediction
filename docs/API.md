## The one thing to understand first

**A refusal is not a low prediction, and you can tell them apart three ways.** This service will decline to answer about a material rather than hand you a number it cannot stand behind, and a caller who mistakes the two will read a refusal as "this alloy is poor" when it means "we do not know".

| | A genuinely low prediction | A refusal |
|---|---|---|
| HTTP status | `200` | `422` |
| `refused` | `false` | `true` |
| `capacity` | present | **the key does not exist** |
| Also carries | `interval`, `domain`, `novelty` | `code`, `explanation`, `screens` |

The third row is the one to rely on. `refused` is a *property* of the answer types rather than a field on them, and a refusal has no field a number could occupy — so there is no way for this service to spell a bare estimate, and no way for a low answer to arrive looking like a decline. Branch on `refused`; the status code agrees with it and is there for clients that only read statuses.

A worked example of the distinction that catches people: `Mg2Ni` at 573 K is **refused**, and not because the estimate is small. The calibrated band came back wider than this project will report, so the honest answer is that the composition is unmeasured — not that it stores little hydrogen. See [`high-uncertainty`](#every-reason-the-service-can-give) below.

## Endpoints

Base path `/v1`, versioned so that a contract change is a new prefix rather than a surprise for whoever wrote a client. The machine-readable contract is committed at `hydms/delivery/api/openapi.json` and gate HG-3 fails while it and the code disagree; the table below is read from that document, not restated beside it.

| | Route | What it answers | Statuses |
|---|---|---|---|
| `GET` | `/v1/health` | Liveness, and which artifact version is answering | `200` |
| `GET` | `/v1/model` | The model card: version, training date, what has been certified, and ranges | `200` |
| `POST` | `/v1/predict` | Predict one composition's capacity at one temperature | `200`, `422` |
| `POST` | `/v1/predict/batch` | Predict many compositions in one request | `200`, `422` |

Run it:

```bash
conda run -n Project uvicorn hydms.delivery.api:app --port 8000
```

**The service resolves one artifact version at startup and answers every request from it.** If no version can be resolved the server does not start. There is no lazy load in a request path, no default version and no unversioned fallback, because a service answering from whatever was on disk cannot say what a number came from. `GET /v1/health` is how a client learns which version it is talking to, and every answer carries `model_version` as well.

## What the interval is, and what it is not

**It is a conformal prediction interval at a nominal 80% level**, in `wt%` on the `capacity` scale, produced by split-conformal calibration (MAPIE) over a CatBoost multi-quantile fit. Both bounds and the level are on every answer, and so are the unit and the space, so a payload crossing the wire still says what it means.

It **is**:

- **Marginal.** Over the calibration distribution, intervals of this kind contain the truth at least 80% of the time. That is an average over candidates, not a promise about yours.
- **At least nominal, never nearer.** Split conformal guarantees *at least* the stated coverage; the finite-sample rank over the calibration rows makes the excess a constant, so a **better** raw fit moves measured coverage further above nominal, not closer to it. Over-coverage is the guarantee working, not a miscalibration.
- **Reported in capacity space**, already `expm1` of the log-space the model is fitted in.

It is **not**:

- **A confidence interval on a parameter.** It is a band around a *future observation*, and it includes the measurement scatter of the underlying experiments.
- **Conditional coverage.** It does not promise that 80 % of the AB₅ alloys you ask about will be covered. Per-family behaviour is what leave-one-alloy-class-out measures, and those figures are on the model card — several of them are poor, and two are negative.
- **A measure of how good the alloy is.** A wide band means the model is uncertain, which is why `high-uncertainty` is a refusal rather than a caveat on a number.
- **Guaranteed positive.** A crossed band — `upper` below `lower` — is possible where quantile heads cross, and it is passed through unclipped on purpose, because clipping would hide the one signal that says the fit disagreed with itself.

## Every reason the service can give

The vocabulary is **derived, never listed**: `reason_codes()` is the union of what the 3 screens on the prediction path declare, plus `admitted` and `indeterminate`. A screen that grows a code widens this table without anything being edited, and a code no screen declares is refused one construction before it could reach you. The sentence beside each code is generated for every path and read by a person on a diff — see [`REFUSALS.md`](REFUSALS.md), which is where the wording lives.

| Code | Declared by | Reachable over HTTP | What you should do about it |
|---|---|---|---|
| `admitted` | the screen contract | yes | Nothing. Every rule that runs was satisfied. Read the interval, not the point estimate — and read the material-versus-system caveat below before comparing the number to a storage target. |
| `above-physical-ceiling` | `domain` | yes | Do not retry. The prediction exceeded what this composition can physically hold at H/M 3, which means the model is wrong about this candidate rather than the candidate being remarkable. Report it: a prediction above the stoichiometric ceiling is a defect in the fit. |
| `beyond-known-chemistry` | `novelty` | yes | This is a statement about the corpus, not about your candidate's merit. The composition is further from every known alloy than any known alloy is from its own nearest neighbour, so the model has no comparable to reason from. It is the refusal an inverse-design programme should expect to meet often, and it is the correct one. |
| `high-uncertainty` | `domain` | yes | Nothing you can fix by rephrasing the question — **this is the answer**. The model will predict here; it cannot do so tightly enough to be worth acting on, and a number with a band this wide tells you less than the training distribution already did. Treat the composition as unmeasured, not as low-capacity. |
| `indeterminate` | `domain`, `novelty`, `temperature` | yes | A rule could not be evaluated at all. Read the sentence: it is usually an unparseable formula or an element outside the property tables, which is a request to fix. It is never a statement that the candidate is poor. |
| `out-of-domain` | `domain` | yes | Treat the estimate as unavailable. The prediction sits above the capacity level that more than one alloy family reaches in training, where the corpus holds one family only — so any answer here is a single family's behaviour generalised to yours. |
| `outside-feature-range` | `domain` | yes | Check which descriptor is named in the sentence; it is the one your composition pushes past the training rows. There is no way to ask this candidate differently, and no version will answer it until the corpus covers that range. |
| `outside-window` | `temperature` | yes | Ask again inside the trained temperature range. The bound is not a modelling convenience: outside it the training rows do not exist, so an answer would be extrapolation with a calibrated-looking band around it. |
| `untrusted-family` | `domain` | **no** | **You cannot receive this over HTTP** — see the reachability note below. It is reachable only by supplying an alloy-class label directly, which the API has no field for. |

**The reachability column is measured, not asserted.** 50 compositions x 10 temperatures were sent through the request door against `v3`, plus the probes above for the two codes a well-formed in-range grid cannot reach. Every declared code was reached except `untrusted-family`, which judges an alloy-class label against that family's measured transfer — and a caller types a formula, not a label. Supplying a guessed one would be worse than omitting it: the screen would answer `indeterminate` for any family it has no transfer estimate for, so every genuinely novel candidate would be refused for the wrong reason. Gate HG-2 goes red if it ever becomes reachable by typing.

*If you are comparing this table with a gate report, they will not match, and neither is wrong.* Gates HG-2 and HG-3 run a fixed set of a dozen probes and record `above-physical-ceiling` and `out-of-domain` as **unreached on this fit** — which is what a small probe set can honestly say, and why the gate marks them as the fit's to decide rather than requiring them. This table is a wider sweep asking a different question: whether *some* typed request reaches the code at all. It does, on `v3`. A code marked reachable here is therefore a lower bound on what a caller can meet, never a promise about any particular candidate.

## The trained ranges, and the applicability domain

These are the spans the screens enforce. They are read off the objects that actually judge, and `GET /v1/model` returns all of them for the version answering you — prefer that over this table, which describes `v3`.

| Quantity | Trained range | Read by |
|---|---|---|
| Temperature | **195 to 773 K** | the `temperature` screen, and its own feature span |
| Capacity (the target) | 0.1 to 7.19 wt% over 893 training rows | — |
| Capacity, cross-family | **at or below 5.19 wt%** — above it the corpus holds 21 row(s) and they are all `Mg` | the `domain` screen |
| 14 model inputs | each has its own trained span; `GET /v1/model` returns all of them | the `domain` screen |

**Which elements the corpus contains.** 50 of them, across 780 distinct canonical compositions in the training split:

> `Ag` `Al` `B` `Ba` `Be` `Ca` `Ce` `Co` `Cr` `Cu` `Dy` `Er` `Fe` `Ga` `Gd` `Ge` `Hf` `Ho` `In` `Ir` `La` `Li` `Mg` `Mn` `Mo` `Nb` `Nd` `Ni` `Os` `Pb` `Pd` `Pr` `Pt` `Re` `Rh` `Ru` `Sc` `Si` `Sm` `Sn` `Ta` `Tb` `Th` `Ti` `Tm` `U` `V` `Y` `Zn` `Zr`

**This is not a bound, and nothing refuses a composition for leaving it.** No screen checks membership of that list: the novelty screen measures *distance* on a chemical scale instead, which is the right rule — an unseen element near a seen one is a better-supported candidate than a seen element in an unseen arrangement. So the list is here because a caller has nowhere else to find it, not because crossing it is an error. Treat it as where the evidence is, and let `beyond-known-chemistry` decide.

9 of the 50 appear in **two compositions or fewer** — `Ge` `In` `Os` `Pb` `Re` `Ru` `Sm` `Tm` `U`. A candidate resting on one of these is supported by one or two measurements, whatever the interval says: the band is calibrated marginally, not conditionally on how much evidence your particular chemistry has.

**The applicability domain is not the same thing as the trained ranges.** A candidate inside every span above can still be refused, because the domain screen also judges the *prediction*: against the composition's own physical capacity ceiling at H/M 3, and against the width of the calibrated band. That is why the order of operations is featurise, predict, **then** screen — a rule that reads a prediction cannot run before one exists.

**Which alloy families this has been shown to work on.** Leave-one-alloy-class-out holds out an entire family and refits, which is the honest test of whether the model transfers to chemistry it has not seen. Measured on `v3`:

|---|---|
| `SS` | +0.763 |
| `A2B` | +0.726 |
| `LEA` | +0.500 |
| `AB` | +0.421 |
| `AB2` | +0.304 |
| `MIC` | +0.280 |

The `domain` screen refuses on that basis, which is why a label it has no measurement for is `indeterminate` rather than admitted.

## Material capacity is not system capacity

Every number this service returns is **gravimetric hydrogen capacity of the material alone**, in `wt%`. It is the mass of hydrogen over the mass of the hydride, and nothing else.

**Do not compare it to a DOE storage target.** Those targets are stated on a *system* basis — they count the tank, the valves, the heat exchanger, and the thermal management a metal hydride needs in order to absorb and release at a useful rate. Comparing a material wt% to a system target is a two-step overstatement: the system figure is strictly smaller than the material figure, often by a large factor, and the gap is engineering rather than chemistry.

A material at 6 wt% is not a system at 6 wt%, and a claim that it meets a 5.5 wt% system target because 6 > 5.5 is wrong twice over. If a number from this service is going into a comparison with a target, say which basis each side is on.

The second thing not to inherit: the published figures in `REPORT.md` were produced by a pipeline with known validation leaks and are **history, not current performance**. Do not quote them beside a number from this service.

## The other door: calling the library directly

The HTTP service computes nothing. Every route is a transport over one function:

```python
from hydms.delivery import predict_capacity

answer = predict_capacity('LaNi5', 298.0)
answer.refused          # False -- or True, and then there is no .capacity at all
answer.to_dict()        # exactly the JSON body the API returns
```

`to_dict()` is not *like* the served body; gate HG-3 sends the same probe set over both doors and requires the served JSON to equal it **value for value**, reporting any difference by JSON pointer. So the two cannot drift, and anything this page says about a response body is equally true of the returned object.

Two differences that are real, and both are deliberate:

- **The library writes nothing.** `predict_capacity()` is pure: no logging, no record, no file. Persisting a served answer is the service's job. See [ADR 0006](adr/0006-the-delivery-seam.md).
- **The library has no batch limit.** `256` is transport policy — how much work one HTTP request may do — and nothing below the API layer knows it.

**Prefer the HTTP door anyway if you have a choice.** It is the path gate HG-3 covers end to end, and the path the Streamlit pages use, so a bug you hit there is a bug everyone hits rather than one your script has to itself.
